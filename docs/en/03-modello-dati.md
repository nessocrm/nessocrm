# Engine data model

All the engine state is one SQLite file: `/data/motore.sqlite` in the `motore-data` volume. Espo has its own MariaDB. The two do not share tables.

## pipeline

One row is an integration.

| Column | Constraint | Meaning |
|---|---|---|
| `id` | primary key | Slug |
| `name` | required | Name on the page |
| `direction` | `in` or `out` | Toward Espo or from Espo |
| `espo_entity` | required | Technical name: `Lead`, `Account`, `Contact` |
| `external_id_field` | required | External column that identifies the record. Outbound, if it is missing, the server writes `id` |
| `key_template` | required | Inbound `modulo-web:{id}`. Outbound an empty string |
| `mapping_json` | required | List of `{from, to, transform}` |
| `key_field` | default `cExternalKey` | Espo field on which the key is looked up and written. Empty if the entity does not accept new fields: the key stays in `chiave` |
| `connection_id` | null allowed | Connection. No foreign key: the value is checked on write |
| `schedule_minutes` | default 0 | 0, 5, 15 or 60 |
| `last_run` | null | `YYYY-MM-DD HH:MM:SS` local to the container |
| `last_status` | null | `ok` or `errore` |
| `last_detail` | null | Text, cut at 500 characters |
| `depends_on` | null | Id of another integration to run first. With a single parent the child starts even if the parent fails |
| `depends_json` | null | List of parents, only when there is more than one. The child starts when all of them are `ok` |
| `write_back` | default 0 | 1 updates the source, and only the fields in `write_fields` |
| `activity_json` | null | Task, call or meeting born with the record, only on creation |
| `portal_json` | null | Visibility rule for a portal. It stays off until it is switched on in Espo |
| `cursor_column` | null | Change column of the inbound database |
| `enabled` | default 1 | 0 pauses the scheduler and the webhook |
| `on_duplicate` | default `fail` | `fail` rejects the similar record with another key. `adopt` updates it |
| `last_success` | null | Time of the last run with at least one row entered, updated, unchanged or closed. A failed run does not move it. If it is empty and the last run is `ok` with aligned rows, home uses `last_run` |
| `expect_at` | null | Time `HH:MM` by which a file is expected. Past that hour, without a success today, `file_alert` becomes 1 |
| `file_alert` | default 0 | 1 until the expected file has a successful run |
| `balance_json` | null | Last balance: counts, keys only on one side, amount gap |

The columns added after the first creation were not in the file of that time. `init_db` adds them with `ALTER` if `PRAGMA table_info` does not see them. An old file still opens.

`/api/pull/{id}` writes the cursor and the sink and does not update `last_run`. A missing external key stops the cursor before the following records. That is why an integration can have rows in `sink_item` and an empty `last_status`. "Run now" goes through `run_pipeline` and does update the three fields.

## connection

| Column | Meaning |
|---|---|
| `id` | Slug |
| `name` | Name on the page |
| `kind` | `webhook`, `database`, `csv`, `http`, `pdf`, `documento`, `sftp`, `ftps` |
| `config_json` | See below. The database password is in clear text in this file, on the local volume |
| `token` | URL-safe secret of 24 bytes. It is born at creation and is not regenerated by an update |

`config_json` by type:

| kind | Content |
|---|---|
| webhook | `{}`, or `signSecret` when the signature is on |
| csv | `{}` |
| http | `url`, the authentication (none, Bearer, basic, a header, or OAuth) and `deliverTo`, the integration the inbox delivers to. Empty: the inbox accumulates |
| database | `host`, `port`, `database`, `user`, `password`, `query` |

The read toward the page removes the password, the signing secret, the client secret and the tokens, and puts the mark that they are there.

## queue_item

Memory of inbound. One row per integration plus external id (`UNIQUE`).

| Column | Meaning |
|---|---|
| `external_id` | Value of the identity column, for example `WEB-77` |
| `payload_json` | Body that arrived from the external system |
| `mapped_json` | Body sent to Espo, key included |
| `hash` | Hex SHA-256 of `mapped_json` with sorted keys |
| `status` | `synced` when the row entered. The reject is not here: it is in `scarto` |
| `espo_id` | Id of the Espo record |
| `detail` | `creato` or `aggiornato`, the last action that wrote |
| `updated_at` | Time of the last write that succeeded |

A reject (409 with another key, missing field, Espo down) does not insert and does not update the row. The external record stays "never seen". On the next run the engine tries the POST again.

`invariato` is not a status of the table. It is only the response when the hash and `status = synced` match. `detail` stays that of the last real write.

## sink_item

Appendix of outbound. Every record read from Espo adds a row, even if the same record had already left in a previous run with a reset cursor. There is no uniqueness. `espo_id` can be empty if Espo did not return `id`.

## cursor_state

One row per integration. Outbound, `cursor_value` is `modifiedAt`, a tab, and the Espo id. If the date is missing, the first part stays empty and the id remains: the next run does not send that id again. Inbound, if there is a change column, it is the last value read, a tab, and the external identity.

## scarto

One row for every record that did not enter or did not leave. It has no uniqueness: the same external id can appear more than once. `payload_json` is cut at 4000 characters, `detail` at 500. Deleting the integration also deletes these rejects.

## run_log

One line for every run, with result and detail. It is the same text as `last_detail`, kept in a queue. The page shows the latest twenty.

## setting, watch_item, field_history, presenza, pending_close

`setting` holds the `writes` switch. `watch_item` is the conflict queue. `field_history` is the previous value and the one written, to undo a run. `presenza` remembers the keys seen, so a complete run knows who disappeared. `pending_close` lists the keys of the first close, waiting for confirmation. `badge_state` remembers, per Espo id, whether the last origin is the ERP or a person, and up to which `modifiedAt` is already seen. Deleting the integration deletes the rows tied to its id. `badge_state` stays, because it hangs on the Espo record.

## delivery

Journal of outbound and of the inbox. It has no uniqueness. A run that sends three leads writes three `inviato` rows. The inbox, receiving those POSTs, writes three `ricevuto` rows with `pipeline_id` null.

| status | Who writes it |
|---|---|
| `inviato` | the HTTP run, after a POST that succeeded |
| `ricevuto` | `POST /inbox/{id}/{token}` |

Deleting an integration does not delete `delivery`. Deleting a connection does not either. The rows stay as a journal.

## chiave

One row ties the external key to the Espo id. It is written on every create and update.

| Column | Meaning |
|---|---|
| `entity` | Espo entity, for example `Team` |
| `external_key` | Full key, for example `team-di-visibilita:TEAM-VNE` |
| `espo_id` | Id of the record |

The primary key is the pair of entity and key. Recognising a link looks here first. If the row is missing and the entity has the field, it still looks in Espo.

Teams, document folders, knowledge categories, roles and email templates do not accept new fields. On those entities `key_field` stays empty, the key does not leave in the JSON and lives only in this table.

## Slug

The name becomes an id like this: lowercase, letters and digits stay, space hyphen and underscore become `-`, `--` is compressed, cut at 40 characters. If the result is empty, the id is `integrazione`. If the id exists, it tries `{base}-2`, then `-3`.

| Name | Id |
|---|---|
| Clienti gestionale verso Account | `clienti-gestionale-verso-account` |
| File notturno | `file-notturno` |
| Lead verso portale | `lead-verso-portale` |

The id enters the external key. Renaming by creating a new integration changes the key and therefore creates new Espo records. Updating the same row through the API, passing the `id`, keeps the key.

## Seed

Only when the `pipeline` table is empty, three rows:

| Id | Direction | Entity | Notes |
|---|---|---|---|
| `modulo-web` | in | Lead | `source` fixed `Web Site`, fixed description. No connection |
| `anagrafica-clienti` | in | Account | also writes `cPartitaIva`. No connection |
| `uscita-lead` | out | Lead | maps id, key, name, email, source, `modifiedAt`. No connection |

They are reachable from `POST /api/ingest/modulo-web` and from `POST /api/pull/uscita-lead`. The current page, in the "New integration" form, requires a connection: these three are not recreated from there.

## Deletions

| Action | Effect |
|---|---|
| `DELETE /api/pipelines/{id}` | deletes the row and the queue, sink, cursor, rejects, journal, conflicts, history, presence and pending closes of that id. It does not touch Espo. Records created in the CRM stay |
| `DELETE /api/connections/{id}` | sets `connection_id` to null on the integrations that used it, then deletes the connection. The integrations stay, without a channel. An inbound integration without a channel, on the next run, answers that a system must be connected |

The page asks for confirmation before deleting.
